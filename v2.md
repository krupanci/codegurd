
An agent (or a person) doesn't need to know which of the three engines
to call. It states the task; CodeGuard decides what to run and returns
a small, ranked bundle of code — each item tagged with *why* it's there
(caller, dependency, blast radius, dead-code candidate) and a one-line,
human-readable reason.

## Why this is different from a plain code-search / RAG tool

A vector index over a codebase (embed chunks, return nearest neighbors)
answers "what looks similar to this text." That's necessary but not
sufficient for an agent about to make a change. CodeGuard is built
around one hand-rolled graph shared by all three features, so what it
returns isn't just "similar" — it's "connected, and here's how":

- Every returned chunk carries its relation to the task (entry point,
  caller, dependency, related-but-unconnected), a hop distance, a
  semantic score, a graph score, and a plain-English reason.
- When the graph is ambiguous (a call could resolve to more than one
  candidate), CodeGuard keeps every candidate rather than silently
  guessing one — it would rather occasionally under-report a dead-code
  finding than ever fabricate one.
- Ranking weights are never a fixed, hand-picked table keyed to a guessed
  "intent." They're derived per query from how confidently the semantic
  search matched and how densely connected the matched code is — so
  accuracy comes from the query and the graph, not from maintaining a
  growing list of hardcoded question categories.

## How it's built

- **Parsing:** tree-sitter, walked by hand (not the `.scm` query
  language) so the project itself understands the tree shape it works
  with.
- **Graph:** fully hand-rolled adjacency maps — no `networkx` — built
  fresh from storage on every run.
- **Storage:** LanceDB, used from the start as the single store for both
  raw facts (chunks, edges) and, later, vectors — not a separate system
  bolted on for search.
- **Embeddings:** local `sentence-transformers`, so indexing and search
  run offline with no API key.
- **Change detection:** git blob hashes, computed the same way `git
  hash-object` does, so staleness checking works without shelling out
  to git and without relying on file timestamps.

## Status

Phases 1–8 (parsing, graph, dead-code detection, change-impact, semantic
retrieval, unified CLI) and Phase 11 (unified context engine,
query-driven ranking) are implemented. Phase 9 (accuracy review against
tricky real-world cases) and Phase 10 (MCP server wrapper, exposing
`get_context` as an agent-callable tool) are next.
